A point-of-sale database for Philippine retail

One data model for pharmacies, convenience and hardware stores. It covers SC/PWD discounts and VAT, clerk-to-cashier order slips, returns and exchanges, and full stock history. You can download it for SQLite, PostgreSQL, MySQL and Supabase.

Decide

Choosing a database

The design comes in three database engines. The cloud options host one of those engines for you, so they use the same files.

OptionWhat it isWorks offlineCostBest for
SQLiteA database inside one file, no serverYesFreeOne computer per database. The simplest v1
PostgreSQLDatabase server you installYes, on the store networkFree software; you run the serverSeveral counters in one store sharing one database
MySQLDatabase server you installYes, on the store networkFree software; you run the serverSame, if the team already knows MySQL
SupabaseHosted PostgreSQL with login and an APINoFree plan; paid tiersMultiple branches or remote reports, without writing a backend
Google CloudCloud SQL: hosted PostgreSQL or MySQLNoPaid; trial credit for new accountsTeams already on Google Cloud or Firebase
AWSRDS / Aurora: hosted PostgreSQL or MySQLNoPaid; free tier for new accountsTeams already on AWS, or larger scale

Cloud prices and free-tier rules change often. Check each provider's current pricing page before deciding.

Online or offline?

A store can't stop selling when the internet drops. That decides most of the architecture.

Local only

SQLite on the counter PC, or PostgreSQL/MySQL on a PC in the store that the counters connect to over the store network. Keeps working without internet; reports are only available in the store.

Cloud only

Supabase, Google Cloud or AWS. The owner can see every branch from anywhere, but checkout stops when the internet is down.

Both

Each counter saves sales to local SQLite and copies them to the cloud when online. The most resilient, but you have to build the syncing, and each counter needs its own invoice number series.

Recommendation

For v1, start with SQLite: no server, works offline, and the design is already tested. If you need the cloud, pick Supabase. It's PostgreSQL with staff login and access rules already written. Choose Google Cloud or AWS when the business already uses them.

Basics

Conventions

These are the same in every version, so the app's calculation code works unchanged whichever database you pick.

WhatStored asExample
MoneyWhole centavos₱112.50 → 11250
QuantityWhole thousandths (_milli)2 pcs → 2000; 1.5 m → 1500
RatesBasis points (_bp)12% → 1200; 20% → 2000
Date/timeTimestamp, reported in store timeAsia/Manila
ChoicesText with an allowed-values liststatus: pending / paid / voided

Whole numbers are used for money and quantities because decimals and floating-point numbers drift (0.1 + 0.2 ≠ 0.3). The app converts to pesos only for display. Every version rejects a value of the wrong type instead of silently storing it.

SQLite only

Every connection must start with PRAGMA foreign_keys = ON;. SQLite leaves table links unchecked by default. PostgreSQL and MySQL always check them.

Structure

Entity relationship diagram

  • A sale is one transactions row with many transaction_items and one or more payments.
  • Each item points to a product and, if discounted, to a discount_type.
  • A return points to the original sale; each return_item points to the exact line that was bought.
  • An exchange is a new sale paid with an exchange_credit payment that points to the return.
  • Every stock change is a stock_movements row; products.stock_milli is their running total.

Flow

How a sale works

  1. Clerk builds the order. Insert a transactions row (status pending, clerk_id). If the customer is SC/PWD, check the ID now and fill in the beneficiary fields, before the slip prints.
  2. Add lines. For each scanned item, insert a transaction_items row with amounts computed as in the discount section. Lines can change freely while pending.
  3. Print the order slip from v_transaction_totals.
  4. Cashier takes payment. Insert one or more payments rows that add up to the amount due.
  5. Mark it paid: UPDATE transactions SET status = 'paid', cashier_id = ?, shift_id = ?. The database checks the items and payments, assigns the next invoice number, freezes the totals and VAT breakdown, and deducts stock.
  6. Print the invoice. From here the lines and payments are locked.
Wrap each step in a database transaction

BEGIN … COMMIT makes the step all-or-nothing: if the app crashes halfway through payment, nothing is half-saved. In single-step stores (two_step_checkout off), the same person does all steps and the slip is skipped.

Tax

SC / PWD discounts and VAT

Discounts are applied to each line, not the whole sale. Each line gets at most one discount; the app picks the best one the customer qualifies for. SC/PWD discounts don't stack with store promos.

CodeWhoWhich productsRateVAT
SC_20Senior Citizensc_pwd class (e.g. medicine)20%Exempt
PWD_20PWDsc_pwd class20%Exempt
SC_BN_5Senior Citizenbasic_necessity class5%Unchanged; weekly cap

Line calculation (done by the app)

gross        = unit_price × qty
if the discount is VAT-exempt (SC/PWD 20%):
    base = round(gross / 1.12)     vat_removed = gross − base
else:
    base = gross                   vat_removed = 0
discount     = round(base × rate)
net          = base − discount
vat          = (tax_treatment = 'vatable') ? net − round(net / 1.12) : 0

Round half up to the centavo, per line. If the store is not VAT-registered, skip the VAT step: the 20% comes straight off the price and every line is non_vat.

After the sale

Returns and exchanges

  1. Find the original sale by the invoice number on the receipt. It must be paid.
  2. Check the return window (return_window_days). Past it, a manager approves and is recorded in approved_by.
  3. Create the return with a reason, then a return_items row per line with quantity, condition and credit. Credit is what the customer actually paid: an SC who paid ₱80.00 for a ₱112.00 box gets ₱80.00 back.
  4. Resellable items go back into stock automatically. Damaged items don't.
  5. Refund: set cash_refund_cents to the total credit.
  6. Exchange: ring up the new items as a new sale, paid with an exchange_credit payment pointing to the return. If the new items cost more, the customer pays the difference; if less, refund the leftover in cash_refund_cents.
Void or return?

Void a sale only when it is cancelled entirely, before the customer leaves. Once anything from a sale has been returned, it can't be voided.

Safety net

Rules the database enforces

These are built into every schema.sql as constraints and triggers, so they hold even if the app has a bug. They were tested on SQLite and PostgreSQL. MySQL has the same rules but hasn't been run yet.

Install

Setup guides

SQLite

Files: sqlite/schema.sql, sqlite/example_checkout.sql.

// Electron + better-sqlite3: run once when the app first starts
const Database = require('better-sqlite3');
const db = new Database(path.join(app.getPath('userData'), 'pos.db'));
db.pragma('journal_mode = WAL');
db.pragma('foreign_keys = ON');          // on every connection
db.exec(fs.readFileSync('schema.sql', 'utf8'));
  • Keep the database file in the app's user-data folder, not the install folder. Back it up daily: a copy of the file is a full backup.
  • Only one computer should write to the file. Don't share it over a network drive; use a server database for that.

PostgreSQL

Files: postgresql/schema.sql, postgresql/example_checkout.sql. Needs PostgreSQL 15 or newer.

createdb pos
psql -d pos -f postgresql/schema.sql
psql -d pos -f postgresql/example_checkout.sql   # optional: sample data
  • Connect from the app with the pg package (Node) or tauri-plugin-sql (Tauri).
  • Times are stored as timestamptz; the daily report converts them using store_settings.time_zone.
  • For a store network, install PostgreSQL on one PC, allow the counters' addresses in pg_hba.conf, and give the app its own database user, not postgres.

MySQL

Files: mysql/schema.sql, mysql/example_checkout.sql. Needs MySQL 8.0.16 or newer (older versions ignore CHECK rules).

mysql -u root -p -e "CREATE DATABASE pos CHARACTER SET utf8mb4"
mysql -u root -p pos < mysql/schema.sql
mysql -u root -p pos < mysql/example_checkout.sql   # optional: sample data
  • Load it with the mysql command-line client. The DELIMITER lines are client commands; some GUI tools need them removed.
  • Set the server time zone to store time, or run SET time_zone = '+08:00' on every connection.
  • Keep the default strict SQL mode so bad values are rejected. Connect with the mysql2 package.
  • XAMPP ships MariaDB, not MySQL. It is very similar, but this schema hasn't been tried on it.
Not yet run

The MySQL files have the same rules as the tested versions, but haven't been run on a MySQL server yet. Test them before relying on them.

Supabase

Files: supabase/migrations/…000000_pos_schema.sql (the PostgreSQL schema) and …000100_auth_and_rls.sql (staff login and access rules).

  1. Create a project in the Southeast Asia (Singapore) region, the closest to the Philippines.
  2. Apply both files in order: supabase db push with the Supabase CLI, or paste each into the SQL Editor.
  3. For each staff member, create a user under Authentication, then link it: update employees set auth_user_id = '…' where employee_id = ….
  4. In the app, log in with supabase.auth.signInWithPassword() and use the normal client. The access rules apply automatically.

CashierClerk permissions, plus: take payments, mark orders paid as themselves, open and close their own shifts, process returns.

  • Never put the service_role key in the POS app; it bypasses every rule. Only the public (anon) key belongs there.
  • Staff can't read pin_hash, so query employees with named columns, not select *.
  • On the free plan, inactive projects can be paused. Check the current plan limits before relying on it for a live store.

Google Cloud

  • Use Cloud SQL for PostgreSQL (with postgresql/) or for MySQL (with mysql/). AlloyDB also takes the PostgreSQL files.
  • Pick region asia-southeast1 (Singapore). For MySQL, set the default_time_zone flag to +08:00.
  • Don't let the counter PCs connect to the database directly over the internet. Put a small backend in between, such as Cloud Run with the Cloud SQL connector. The desktop app talks to that backend, which checks who the user is.
Firebase / Firestore isn't a good fit

It's a document database with no table links, CHECK rules or triggers, so every built-in rule would have to be rewritten as Cloud Functions. Sales and stock data is relational. If you want Firebase, use Firebase Authentication with Cloud SQL, or Firebase Data Connect, which runs on Cloud SQL for PostgreSQL.

AWS

  • Use RDS for PostgreSQL or Aurora PostgreSQL (with postgresql/), or RDS for MySQL or Aurora MySQL (with mysql/).
  • Pick region ap-southeast-1 (Singapore). For MySQL, set time_zone in a DB parameter group.
  • Keep the database private, not publicly accessible. Put a backend in between, such as Lambda + API Gateway or a small server on ECS/EC2, and keep credentials in Secrets Manager.
  • Turn on automated backups and choose a retention period.
DynamoDB isn't a good fit

Same reason as Firestore: no table links, CHECK rules or triggers.

Still to do

What the app must do, and open items

The app is responsible for

  • SQLite: PRAGMA foreign_keys = ON on every connection.
  • Cloud databases: going through a backend or Supabase login, never embedding database admin credentials in the desktop app.
  • Computing each line's VAT and discount before saving it.
  • Converting pesos to centavos.
  • Choosing the best discount per line, and enforcing the weekly cap on basic necessities.
  • Checking the return window, and asking for a manager PIN for voids and late returns.
  • Checking role permissions (Supabase enforces these itself).
  • Hashing PINs, and computing expected cash when a shift closes.

Open items

  • Weekly cap for SC_BN_5: left empty; set it from the current DTI order.
  • 5% basic necessities for PWD: not seeded; check whether current rules extend it to PWDs.
  • Refunds in the end-of-day report: v_daily_sales shows sales only; add refunds from returns.
  • Invoice layout and BIR registration: confirm required fields with BIR or an accountant.
  • Offline sync: if you combine local SQLite with a cloud database, the syncing and per-counter invoice series still need designing.
  • Testing: SQLite 3.45 and PostgreSQL 18 tested; Supabase rules tested with a login stand-in; MySQL not yet run; none run through Electron or Tauri yet.
