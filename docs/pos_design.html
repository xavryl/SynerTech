1. Conventions

WhatStored asExample
MoneyINTEGER centavos₱112.50 → 11250
QuantityINTEGER thousandths (_milli)2 pcs → 2000; 1.5 m → 1500
RatesINTEGER basis points (_bp)12% → 1200; 20% → 2000
Date/timeTimestamp, reported in store time (Asia/Manila)2026-10-26 14:05:00
Yes/no0/1 in SQLite, boolean elsewhereis_active
ChoicesTEXT with a CHECK liststatus IN ('pending','paid','voided')

Whole numbers are used for money and quantities because decimals and floating-point numbers drift (0.1 + 0.2 ≠ 0.3). The app converts to pesos only for display.

These conventions are the same in every version, so the app's calculation code works unchanged whichever database you pick. PostgreSQL and MySQL could store money as NUMERIC/DECIMAL instead, but then the app would need different code for SQLite.

Every version rejects a value of the wrong type, such as '112.50' in a centavo column, instead of silently storing it. SQLite does this through STRICT tables, and MySQL through its default strict SQL mode.

SQLite only: every connection must start with PRAGMA foreign_keys = ON;. SQLite leaves foreign keys off by default, and without this line none of the table links are checked. PostgreSQL and MySQL always check them.

Online or offline?

A store can't stop selling when the internet drops. That decides most of the architecture:

  • Local only: SQLite on the counter PC, or PostgreSQL/MySQL on a PC in the store that the counters connect to over the store network. Keeps working without internet. Reports are only available in the store.
  • Cloud only: Supabase, Google Cloud or AWS. The owner can see every branch from anywhere, but checkout stops when the internet is down.
  • Both: each counter saves sales to local SQLite and copies them to the cloud database when online. This is the most resilient, but it's also the most work: you have to build the syncing. Each counter also needs its own invoice number series, because two offline counters can't share one counter.
Recommendation For v1, start with SQLite: no server, works offline, and the design is already tested. If you need the cloud, pick Supabase. It's PostgreSQL with staff login and access rules already written in supabase/migrations/. Choose Google Cloud or AWS when the business already uses them.

4. Entity relationship diagram

Reading the diagram

  • A sale is one transactions row with many transaction_items and one or more payments.
  • Each item points to a product and, if discounted, to a discount_type.
  • A return points to the original sale; each return_item points to the exact line that was bought.
  • An exchange is a new sale paid with a payments row of method exchange_credit that points to the return.
  • Every stock change is a stock_movements row; products.stock_milli is their running total.

6. How a sale works

Steps

  1. Clerk builds the order. Insert a transactions row (status pending, clerk_id). If the customer is SC/PWD, check the ID now and fill in the beneficiary fields, before the slip prints.
  2. Add lines. For each scanned item, insert a transaction_items row with the amounts computed as in Section 7. Lines can be changed freely while pending.
  3. Print the order slip from v_transaction_totals.
  4. Cashier takes payment. Insert one or more payments rows that add up to the amount due.
  5. Mark it paid: UPDATE transactions SET status = 'paid', cashier_id = ?, shift_id = ?. The database then:
    • checks there are items and the payments match the amount due,
    • assigns the next invoice number and the paid time (PostgreSQL and MySQL take it from invoice_counter),
    • copies the totals and VAT breakdown onto the transaction,
    • deducts stock through stock_movements.
  6. Print the invoice. From here the lines and payments are locked.
Wrap each step in a database transaction BEGIN … COMMIT makes the step all-or-nothing. If the app crashes halfway through payment, nothing is half-saved. In single-step stores (two_step_checkout = 0), the same person does all steps and the slip is skipped.

7. SC / PWD discounts and VAT

Discounts are applied to each line, not the whole sale. Each line gets at most one discount; the app picks the best one the customer qualifies for. SC/PWD discounts do not stack with store promos.

CodeWhoWhich productsRateVAT
SC_20Senior Citizendiscount_class = 'sc_pwd' (e.g. medicine)20%Exempt
PWD_20PWDdiscount_class = 'sc_pwd'20%Exempt
SC_BN_5Senior Citizendiscount_class = 'basic_necessity'5%Unchanged; weekly cap

Line calculation (done by the app)

gross = unit_price × qty if the discount is VAT-exempt (SC/PWD 20%): base = round(gross / 1.12) vat_removed = gross − base else: base = gross vat_removed = 0 discount = round(base × rate) net = base − discount vat = (tax_treatment = 'vatable') ? net − round(net / 1.12) : 0

Round half up to the centavo, per line. If the store is not VAT-registered, skip the VAT step: the 20% is taken straight off the price and every line is non_vat.

ItemQtyGrossVAT removedDiscountNet
Paracetamol 500mg, box (₱112.00, SC_20)2224.0024.0040.00160.00
Rice, per kg (₱56.00, VAT-exempt item, SC_BN_5)2 kg112.000.005.60106.40

One box of paracetamol: ₱112.00 ÷ 1.12 = ₱100.00 without VAT, less 20% = ₱80.00.

The invoice shows VAT-exempt sales before the SC discount (₱312.00 here), then the discount on its own line. This is the usual layout, but confirm it with your accountant or BIR.

For the 5% basic-necessities discount, the app must add up this beneficiary's purchases over the past 7 days (by beneficiary_id_no) and stop applying it once the weekly cap is reached.

8. Returns and exchanges

  1. Find the original sale by invoice number from the receipt. It must be paid.
  2. Check the return window (return_window_days). Past it, a manager approves and is recorded in approved_by.
  3. Create the return with a reason, then a return_items row for each line, with the quantity, condition and credit. Credit is what the customer actually paid: an SC who paid ₱80.00 for a ₱112.00 box gets ₱80.00 back, not ₱112.00.
  4. Resellable items go back into stock automatically. Damaged items do not.
  5. Refund: set cash_refund_cents to the total credit.
  6. Exchange: ring up the new items as a new sale. Pay it with a payments row of method exchange_credit pointing to the return.
    • If the new items cost more, the customer pays the difference with another payment.
    • If they cost less, refund the leftover in cash_refund_cents.
Void or return? Void a sale only when it is cancelled entirely, before the customer leaves. Once anything from a sale has been returned, it can no longer be voided.

9. Rules the database enforces

These are built into every schema.sql as constraints and triggers, so they hold even if the app has a bug. They were tested on SQLite and PostgreSQL. The MySQL version has the same rules but has not been run yet (Section 11).

RuleWhat happens
Wrong data typeRejected (e.g. text or 112.50 in a centavo column)
Line amounts don't add upRejected: net must equal gross − VAT removed − discount

Paying an empty order, or payments ≠ amount dueRejected

Editing lines or adding payments after paymentRejected: "transaction is no longer pending"
Deleting a transactionRejected: void it instead
Void without who, when and whyRejected
Voiding a paid saleStock put back. Rejected if the sale has returns
Changing a voided transaction, or going back to pendingRejected
SC/PWD without ID number or nameRejected
Returning an item from a different sale, or more than was boughtRejected
Exchange credit plus cash refund more than the return is worthRejected
Any stock movementproducts.stock_milli updated to match

Creating a sale that is already marked paidRejected: every sale starts as a pending order

10. Setting up each database

SQLite

Files: sqlite/schema.sql, sqlite/example_checkout.sql.

  • When the app first starts, create the database file and run schema.sql once. With Electron and better-sqlite3: db.exec(fs.readFileSync('schema.sql', 'utf8')).
  • Run PRAGMA foreign_keys = ON on every connection, and PRAGMA journal_mode = WAL once.
  • Keep the database file in the app's user-data folder, not the install folder, and back it up daily (a copy of the file is a full backup).
  • Only one computer should write to the file. Don't share it over a network drive; use a server database for that.

PostgreSQL

Files: postgresql/schema.sql, postgresql/example_checkout.sql. Needs PostgreSQL 15 or newer.

createdb pos psql -d pos -f postgresql/schema.sql psql -d pos -f postgresql/example_checkout.sql # optional: sample data
  • Connect from the app with the pg package (Node) or tauri-plugin-sql (Tauri).
  • Times are stored as timestamptz (UTC inside). The daily report converts them using store_settings.time_zone.
  • For a store network, install PostgreSQL on one PC, allow the counters' addresses in pg_hba.conf, and give the app its own database user, not postgres.

MySQL

Files: mysql/schema.sql, mysql/example_checkout.sql. Needs MySQL 8.0.16 or newer (older versions ignore CHECK rules).

mysql -u root -p -e "CREATE DATABASE pos CHARACTER SET utf8mb4" mysql -u root -p pos < mysql/schema.sql mysql -u root -p pos < mysql/example_checkout.sql # optional: sample data
  • Load it with the mysql command-line client. The DELIMITER lines in the file are client commands; some GUI tools need them removed.
  • Set the time zone to store time on the server, or run SET time_zone = '+08:00' on every connection.
  • Keep the default strict SQL mode so bad values are rejected.
  • Connect from the app with the mysql2 package.
  • XAMPP ships MariaDB, not MySQL. It is very similar, but this schema has not been tried on it.

Supabase

Files: supabase/migrations/20261026000000_pos_schema.sql (same as the PostgreSQL schema) and …000100_auth_and_rls.sql (staff login and access rules).

  1. Create a project in the Southeast Asia (Singapore) region, the closest to the Philippines.
  2. Apply both files in order: supabase db push with the Supabase CLI, or paste each into the SQL Editor.
  3. For each staff member, create a user under Authentication, then link it: update employees set auth_user_id = '…' where employee_id = ….
  4. In the app, log in with supabase.auth.signInWithPassword() and use the normal client. The access rules apply automatically.

  • Never put the service_role key in the POS app; it bypasses every rule. Only the public (anon) key belongs there.
  • Staff can't read pin_hash, so query employees with named columns, not select *.
  • On the free plan, inactive projects can be paused. Check the current plan limits before relying on it for a live store.

Google Cloud

  • Use Cloud SQL for PostgreSQL (with postgresql/) or Cloud SQL for MySQL (with mysql/). AlloyDB also takes the PostgreSQL files.
  • Pick region asia-southeast1 (Singapore). For MySQL, set the default_time_zone flag to +08:00.
  • Don't let the counter PCs connect to the database directly over the internet. Put a small backend in between, such as Cloud Run, connected through the Cloud SQL connector. The desktop app talks to that backend, which checks who the user is.
  • Firebase / Firestore is not a good fit. It's a document database with no table links, CHECK rules or triggers, so every rule in Section 9 would have to be rewritten as Cloud Functions. Sales and stock data is relational. If you want Firebase, use Firebase Authentication with Cloud SQL, or Firebase Data Connect, which runs on Cloud SQL for PostgreSQL.

AWS

  • Use RDS for PostgreSQL or Aurora PostgreSQL (with postgresql/), or RDS for MySQL or Aurora MySQL (with mysql/).
  • Pick region ap-southeast-1 (Singapore). For MySQL, set time_zone in a DB parameter group.
  • Keep the database private (not publicly accessible). Put a backend in between, such as Lambda + API Gateway or a small server on ECS/EC2, and keep credentials in Secrets Manager.
  • Turn on automated backups and choose a retention period.
  • DynamoDB is not a good fit, for the same reasons as Firestore.

11. What the app must do, and open items

The app is responsible for

  • SQLite: running PRAGMA foreign_keys = ON on every connection.
  • Cloud databases: going through a backend or Supabase login, never embedding database admin credentials in the desktop app.
  • Computing each line's VAT and discount (Section 7) before saving it.
  • Converting pesos to centavos. The database can't tell 112 meant as ₱112.00 from 112 centavos.
  • Choosing the best discount for each line, and enforcing the weekly cap on basic necessities.
  • Checking the return window, and asking for a manager PIN for voids and late returns.
  • Checking role permissions (clerk / cashier / manager).
  • Hashing PINs (bcrypt or argon2).
  • Computing expected_cash_cents when a shift closes.
